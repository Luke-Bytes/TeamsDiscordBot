# Minecraft Java username history

`/name history username:<current IGN>` is a guild-only, ephemeral, read-only lookup; the player does not need to be registered. It defers before networking, has a per-user 30-second cooldown, and shows canonical IGN, UUID, distinct visible historical names, dates, sources and coverage. Long reports use up to four private embed messages and an attached text list if necessary. Do not distribute private results. This is not `/username update`; no account mutation occurs.

`/modcheck` shows a combined UUID-linked summary for the stored primary UUID alongside its existing player-wide records. Neither missing nor abundant history changes alt-account diagnostics or punishments. Navi knows the command exists but has no history tool.

## Service

`MinecraftNameHistoryAPI.lookup(username)` uses the existing MojangAPI lookup and reverse lookup to verify current identity, including real canonical casing and the response UUID. If the cached IGN now belongs to a different account, it bypasses the existing short resolution cache once. No previous name is resolved recursively. `lookupByUUID(uuid)` accepts dashed or undashed UUIDs; a failed reverse lookup is unavailable (the existing reverse API does not distinguish absence and outages). The normalised identity is a lowercase, undashed UUID. Current name is included even if every history source fails.

The API returns typed name groups with casing variants, provider evidence and per-source record order, earliest dated evidence, latest observation, best date, possible conflicting dates, and provider statuses. Case-insensitive duplicates are merged, not counted as extra renames. Repeated usage records are preserved separately without inventing a unified timeline. The source dates are not independent corroboration. Provider-reported accurate change dates are preferred over observations; the earliest Laby record can be an account creation date so is generically labelled, not assumed a rename. Date-only values remain dates; impossible and implausibly future dates are rejected. Names with invalid dates can still be shown.

## Local database source

The shared service also reads the Friendly Wars database, without any schema changes or credentials. It looks up a unique Player by its stored primary Minecraft UUID (case-insensitive, dashed or undashed) and uses its paired latestIGN, plus EventSignup UUID/name pairs scoped to the invoking guild. These are recorded associations, not independent proof of a rename; dates are unknown because player and signup identities can be rewritten. Unregistered accounts may still have event records. Ambiguous duplicate primary links are not attributed to either player.

An organiser using `/name history` also sees additional names from that player's saved minecraftAccounts and finished GameParticipation.ignUsed records across seasons, deduplicated separately and excluding names already in the UUID-linked list. Game start times are observations of the recorded IGN, not rename dates. These records lack a historical UUID and can belong to different accounts; they are explicitly labelled UUID-unverified and excluded from the UUID-linked count. Ordinary members cannot access this additional player-linked list. `/modcheck` already has its own organiser-only player-wide record section. The service accepts an optional guildId and trusted organiser-only includePlayerRecords scope; without a guildId it does not query event signups.

Local records are read afresh, in parallel with external sources, with a 4.5-second response deadline and eight outstanding reads maximum. Per-source row caps (500 signup records, saved names and matches each) and ambiguous/failed reads are reported as limited; database failure does not erase external evidence. A timed-out Prisma operation may continue until the database driver settles; its concurrency slot stays occupied. Suppression covers both UUID-linked and player-linked database results. No Discord IDs, answers or unrelated event details are returned.

| MCProfiles | Enabled by default; no key | [Docs](https://mcprofiles.me/docs): GET `https://mcprofiles.me/api/player/{uuid}`; `{kind,data,meta}`, `data.uuid`, `data.usernameHistory: [{username,observedAt}]` | 10/10s upstream, local 10/30s; observed dates, not rename times. Accepts UUID-matched profile/archiveFallback only; records cache/stale metadata. |
| Bisai | `BISAI_API_KEY` | [Docs](https://mc-api.bisai.dev/docs), [OpenAPI](https://mc-api.bisai.dev/v1/openapi.json): GET `/v1/profile/{uuid}/names?limit=500`; `X-API-Key`; `{uuid,total,limit,offset,names:[{name,occurrence,first_seen,last_seen}],note}` | One credit per lookup. Results above 500 are explicitly limited. |

The two published schema examples and access/attribution rules were independently confirmed in indexed provider documentation. Winstreak's terms also require an identifying User-Agent and source link; both providers are linked in the command. No production credentials were used; authenticated live samples could not be obtained. No legacy Laby username-field variant was independently established, so the parser uses the documented name field only. Neither documented history response includes an account UUID; the request is UUID-bound and any returned UUID field is checked rather than accepting a contradictory response.

Direct, small public sample requests from the development workspace confirmed HTTP 200 for MCProfiles (Notch UUID; dashed data.uuid and observedAt history) and Bisai (jeb_ UUID; paginated names with occurrence, first_seen and nullable last_seen). Bisai's OpenAPI JSON also returned HTTP 200. A subsequent Bisai sample reported x-credits-limit=1200, x-credits-remaining and x-credits-reset; the authenticated quota and shared-IP reset-window allowance were not established. [Terms](https://mc-api.bisai.dev/terms) permit ordinary anonymous use, but describe individual-user IPs as intended; the bot conservatively requires a key. [Privacy](https://mc-api.bisai.dev/privacy) provides removal/objection handling. MCProfiles omits privacy-suppressed profiles; silent absence cannot distinguish removal from an unknown account.

MCProfiles is always queried for non-suppressed accounts without credentials. The other providers are automatically used when their authorised credential is non-empty; remove the credential to stop using that provider. Missing credentials are normal and do not prevent startup. The optional UUID suppression list below is independent of provider configuration.

### Investigated but not implemented

- [Crafty](https://crafty.gg/public-api): documented token-based GET `/api/v2/players/{username}` does not establish a history response schema or UUID input support. No undocumented endpoints or scraping.
- [Ashcon](https://github.com/Electroid/mojang-api): legacy name history relied on the removed Mojang endpoint; public test request returned HTTP 429 and useful current coverage/privacy could not be established.
- [PlayerDB](https://playerdb.co/): official schema documents current identity, not name history.
- NameMC: no verified supported JSON history endpoint. [Liforra](https://github.com/liforra/namehistory-minecraft): associated backend uses scraping; excluded. No verified additional supported history APIs found.
- Mojang retired its public name-history endpoint in September 2022; it is not used here.

## Reliability and privacy

Only fixed HTTPS endpoints and UUID-based requests are used. MCProfiles returns additional profile information, which is discarded and never retained or logged; only necessary name/date evidence is parsed. Responses are streamed with a 256 KiB limit, capped at 500 rows per source, and parsed defensively. Redirects are rejected to prevent credential forwarding. Provider requests run concurrently and independently with 4.5-second abort timeouts; no upstream retries. Existing Mojang retry windows are allowed for within a 50-second lookup budget. At most eight distinct in-flight identity/history lookups and bounded upstream per-provider request windows. Repeated UUID requests coalesce.

Winstreak and Bisai successful results are cached for up to 10 minutes, MCProfiles for up to two minutes, shortened or disabled by response cache headers (Bisai's sampled response was no-cache); Laby success is not cached. Failures cool down for 15 seconds, and HTTP 429 activates a provider-wide Retry-After cooldown. The total cache is bounded at 500 entries. No fetched external history is persisted to Prisma; existing local records are read only; no raw responses or authentication headers are logged. The user-command audit may record the requested current IGN under the existing audit policy.

Explicit profile/record redaction signals cause conservative suppression of the merged historical result and retain an in-memory suppression marker until restart. The marker set is bounded; if it fills, history fails closed until restart. A null Laby date can be unknown or hidden, so the date for that name is not reconstructed from another source. Providers can silently omit records; there is no way to infer from the API whether every omission is a privacy choice. Do not use another service to intentionally recover a withheld name. To honour a removal request, add the affected UUID to `MC_NAME_HISTORY_SUPPRESSED_UUIDS` (comma/whitespace separated) and restart or update the process environment; call `MinecraftNameHistoryAPI.invalidate(uuid)` for immediate cache invalidation in a running integration. Invalidation also prevents old in-flight evidence from being published/cached. Suppression retains only the verified current name, with no history provider requests. This does not revoke private messages already delivered; request deletion separately if needed.

## Adding a provider

Verify supported backend access, response schema, UUID binding, date precision and privacy/terms before adding an adapter to `NameHistoryProviders.ts`. Add a specific parser and typed provider ID, attribution and rate/cache limits; do not reuse a parser by guessing similar field names. Register sanitized offline fixtures and tests for malformed, withheld, mismatched, truncated and failed results. Never scrape or use production credentials for tests.
